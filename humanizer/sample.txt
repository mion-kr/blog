개인 프로젝트로 운영하는 게임 정보 사이트 홈에는 쿠폰과 공지가 나온다. 게임 공식 포럼의 공개 API에서 글을 읽어 와서, 15분마다 다시 갱신(재검증)하는 구조다. 재검증은 Vercel의 운영 서버 함수(요청을 처리하는 서버리스 함수)가 맡는다.
어느 날 공식 포럼에 올라온 새 쿠폰 2개가 홈 쿠폰 목록에 없는 것을 발견했다.
홈은 에러 화면 없이 정상으로 보였다. 포럼 요청이 실패하면 미리 저장해 둔 저장본(snapshot)을 보여 주게 만들어 뒀기 때문이다.
이 대비책 덕분에 사용자는 에러 화면을 보지 않았지만, 같은 이유로 나는 실패를 알아채지 못했다. 운영 로그를 보니 포럼 요청이 계속 403(접근 거부)으로 실패하고 있었다. 그동안 홈은 오래된 저장본을 보여 주고 있었다.
같은 요청을 로컬에서 직접 보내 봤다.
실제 Chrome의 User-Agent는 버전을 점으로 구분한 숫자 네 개(130.0.0.0)로 쓴다. 코드에는 숫자 두 개로 적혀 있었다. 포럼 앞단의 필터가 형식이 맞지 않는 User-Agent를 막기 시작한 것으로 보인다. 필터가 언제부터, 정확히 어떤 규칙으로 바뀌었는지는 알 수 없다.
같은 값이 세 파일(운영 서버 함수 하나, 저장본 생성 스크립트 둘)에 흩어져 있었다. 이번에는 세 곳을 모두 고치고 주석을 달았다. 하나로 모으는 일은 후속 과제로 남겼다.
이 필터가 브라우저가 아닌 호출을 막으려는 의도인지는 확인하지 못했다. 공개 API라도 상대 서비스의 이용 규칙은 지켜야 하므로, 포럼 이용 약관을 다시 확인하고 호출 주기는 15분으로 유지하기로 했다.
로컬에서 200이 나오고, 저장본을 다시 받으니 쿠폰 9개가 들어왔다. 테스트와 빌드도 통과했다.
다만 그때는 운영 서버 함수에서도 통과하는지 아직 확인하지 못한 상태였다. 로컬과 빌드 머신은 운영 서버 함수와 IP가 달라서, 필터가 IP까지 보고 있다면 결과가 다를 수 있다.
배포 직후 화면은 빌드 머신이 읽은 데이터다. 운영 서버 함수가 직접 읽은 데이터는 15분 재검증이 지나야 나온다.
에러 로그도 다시 봤다. 마지막 403은 새 배포가 만들어지기 전 시각이었고, 그 뒤로 확인한 시점까지는 0건이었다.
이번 일에서 고칠 점은 403을 늦게 알았다는 것이다. 저장본으로 대체하는 설계는 유지하되, 실패가 계속되면 내가 알 수 있어야 한다.
저장본 안내 문구가 화면에 나오는지 주기적으로 확인하고, 같은 외부 API 실패가 일정 횟수 이상 이어지면 알림을 받도록 할 계획이다. 둘 다 아직 붙이지는 않았다.

개인 프로젝트로 게임 정보 사이트를 운영하면서 할 일이 한꺼번에 늘었다. 아이템 도감, 계산기, 헤더 검색, 모바일 레이아웃 수정이 동시에 쌓였다.
코딩 에이전트 하나와 대화하며 순서대로 처리하기에는 너무 느렸다.
할 일 하나마다 Linear 이슈를 하나 만들고, 그 이슈에 연결된 git 워크트리 하나에서 에이전트 하나가 일한다.
같은 저장소에서 여러 에이전트가 동시에 브랜치를 바꾸면 서로의 작업 트리를 망가뜨린다. 워크트리는 브랜치마다 작업 폴더가 따로 있어서 이 문제가 없다.
워크트리와 터미널 관리는 Orca를 썼다. Orca는 워크트리마다 터미널과 브라우저 탭을 묶어 관리하고, 에이전트를 띄워 감독하는 오케스트레이션 명령을 제공한다.
이슈 생성부터 에이전트 실행까지의 시작 절차(킥오프)를 스킬 하나로 묶었다. 스킬은 에이전트가 필요할 때 불러 읽는 절차 문서다.
써 보면서 고친 점도 있었다.
처음에는 파일 복사를 새 에이전트에게 프롬프트로 시켰다. 그런데 에이전트가 이 지시를 빠뜨리면 .env 없이 작업이 시작될 수 있었다. 그래서 원본 세션이 먼저 복사하고 확인한 뒤에 에이전트를 실행하도록 순서를 바꿨다.
작업자의 보고는 그대로 믿지 않고 총괄이 다시 확인했다. 예를 들어 팀원이 보고한 사이트 이름을 총괄이 소스 파일에서 직접 대조했다.
감독형 작업자는 기본 1단계까지만 허용된다. 설정에서 깊이를 늘릴 수 있지만, 감독 계층이 깊어질수록 실패가 연쇄로 번질 위험이 커진다.
작업자가 새 실행 단위를 만들면 메시지가 끊긴다. Orca 오케스트레이션은 감독 작업 묶음을 Run이라는 단위로 관리한다. 작업자가 새 Run을 만들면 메시지를 받는 곳도 새 Run으로 바뀌어, 총괄이 보내는 후속 메시지가 작업자에게 닿지 않는다. 중첩 구조에서 가장 피해야 할 함정이었다.
결재 기준도 정했다. 기술 선택이나 저장소 규칙으로 답이 정해지는 질문은 총괄이 처리한다. 요구사항, 병합·배포, 비용, 설정 변경, 데이터 삭제, 외부 게시는 나에게 올라온다.
PR 여러 개가 병렬로 올라오니 처리 속도는 확실히 빨라졌다. 대신 내 일이 "코드 작성"에서 "결과 검수"로 바뀌었다. 스크린샷을 보고 "390px에서 표가 잘린다"고 돌려보내는 일이 많아졌다.
병렬로 일하면 충돌도 병렬로 생긴다. 앞선 PR이 병합되면 다른 브랜치를 그 위로 다시 맞추고 검증을 다시 돌려야 했다. 그래서 배포 순서를 총괄이 정하고, 뒤 순서 작업은 로컬 커밋만 해 둔 채 신호를 기다리게 했다.

오늘 주니어 개발자에게 들려준 이야기를 정리한다.
복잡성을 해결할 은탄환 같은 건 없다. 기술 스택을 바꾸거나 새로운 아키텍처를 도입하거나 특정 패턴을 적용해도 복잡성은 갑자기 사라지지 않는다.
대신 시간이 지날수록 늘어나는 복잡성이 관리 가능한 형태로 남도록 설계할 수는 있다.
설계가 팀 안에서 오래 유지되려면 왜 이렇게 설계했는지 설명할 수 있어야 한다. 이 설명은 코드 자체만큼 중요하다.
관계가 깊은 도메인에서는 하위 데이터가 상위 관계를 전부 가지게 하는 선택이 자주 나온다.
오늘 주니어 개발자와 이야기한 사례는 파트너 메모가 예약에 붙는 구조였다. 예약은 한 종류로 고정되지 않았다. 비즈니스 흐름상 메모는 카드 예약, 무통장 예약, 오프라인(자체) 예약 중 어느 것에든 연결될 수 있었다.
이 선택에는 분명 실용적인 편의가 있지만 부작용도 함께 따라온다. 그래서 코드 리뷰를 요청할 때는 편하다는 이유 외에, 이 방식이 지금 도메인에서 왜 합리적인지도 설명할 수 있어야 한다.
조회가 쉽다는 것도 이유가 될 수 있지만 그것만으로는 부족하다. 설계에는 언제나 비용이 따르므로, 리뷰에서 설득력 있는 설명은 보통 얻는 것과 감수하는 것을 함께 놓는다.
이 트레이드오프가 정리되지 않으면 리뷰어는 그 설계를 "이유 없는 편의"로 보게 된다. 반대로 트레이드오프가 정리되어 있으면 리뷰는 "맞냐/틀리냐" 대신 "위험을 어떻게 관리하냐"를 묻게 된다.
어떤 구조를 검토할지는 전제에 따라 달라진다. 예를 들어 예약 유형이 당분간 세 개로 고정되고, 메모가 반드시 그중 하나에 속한다고 가정한다. 이 전제라면 여러 외래 키와 연결 개수 제약을 검토할 수 있다.
반면 예약 유형이 계속 늘고 여러 기능에서 같은 예약을 참조한다면, 공통 예약 모델을 검토할 이유가 커진다.
유형과 식별자만 저장하는 방식도 있다. 이 방식은 컬럼 추가를 줄이지만, 서로 다른 대상 테이블의 존재를 일반 외래 키 하나로 보장하기 어렵다.
조회가 빨라진다는 주장은 실제 쿼리와 실행 계획을 비교한 뒤에 붙일 수 있다.
복잡성은 계속 늘어나고 설계로 없앨 수도 없다. 좋은 설계는 그 복잡성을 관리 가능한 형태로 정리하고, 팀이 납득할 수 있는 이유를 남긴다.
누군가 메모가 상위 관계를 전부 들고 있게 했다면, 질문은 그 선택이 맞는지에서 무엇을 얻었고 감수한 비용을 어떻게 관리할지로 바뀌어야 한다.

회사에서 운영하던 Next.js 서비스 하나를 Vercel에서 AWS로 옮겼다.
계기는 봇 대응이었다. 공개 API 몇 개에 호출 제한을 넣고 봇을 막아야 했다. 그런데 Vercel 공식 문서는 Vercel 앞에 다른 프록시를 두는 구성을 권장하지 않는다.
회사의 다른 서비스는 이미 AWS ECS에서 돌고 있었다. 그래서 이참에 Vercel 의존성을 없애고 운영 방식을 하나로 맞추기로 했다.
옮기기 전에 저장소에서 Vercel 전용 기능을 찾아봤는데, 묶인 부분이 예상보다 적었다.
처음 구성하는 입장에서는 공식 지원 범위 안에 있는 쪽이 안전하다고 보고 ECS로 정했다.
기존 ALB와 Redis를 같이 쓰면 이 서비스에 요청이 폭주할 때 다른 서비스에도 영향을 줄 수 있다. 그래서 호출 제한과 키 접두사로 영향을 줄였다.
네임서버를 바꾸는 시점에는 레코드가 여전히 같은 곳(Vercel)을 가리키므로 중단이 없다. 실제 전환은 그 뒤에 레코드 한 줄을 바꾸는 작업이다.
이제 인증서 자동 갱신은 Cloudflare에 있는 검증 CNAME 2개에 의존한다. 나중에 누군가 "안 쓰는 레코드"로 보고 지우면 인증서 갱신이 실패한다. 그래서 이 사실을 Terraform 주석과 PR 본문에 남겼다.
며칠 뒤 Cloudflare 로그에서 실제 구글봇이 "AI 학습 크롤러 차단" 규칙에 걸리고 있는 것을 발견했다.
요청을 다시 세어 보니 3일 동안 구글봇의 페이지 요청 6건이 전부 403이었다. 통과한 것은 robots.txt와 favicon.ico뿐이었다.
원인은 "Block" 설정이 막는 범위에 있었다. Cloudflare AI Crawl Control 화면의 학습 정책을 "Block"으로 두면 검색과 학습을 겸하는 크롤러까지 함께 막는다. 구글봇과 빙봇은 화면에서 개별 스위치가 잠겨 있어 따로 풀 수도 없었다.
Cloudflare 공식 블로그가 안내하는 대로 학습 정책을 "Disallow"로 바꿨다.
설정이 저장된 것과 사칭 요청이 계속 막히는 것은 확인했다. 실제 구글봇이 이제 200을 받는지는 구글봇이 다시 와야 알 수 있다. 이 글을 쓰는 시점에는 아직 확인하지 못했다.
