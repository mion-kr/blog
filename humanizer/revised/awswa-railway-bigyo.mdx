이 블로그를 만들며 나는 Railway를 처음 접했다. 그 뒤로 AWS와의 차이점을 명확히 이해하고 싶다는 피드백을 여러 차례 받았다.

두 플랫폼은 서비스 모델, 인프라 구성, 배포 방식 등 여러 측면에서 다르다. 그래서 주요 항목을 비교했다.

아래 제품 설명의 확인 기준일은 2026년 9월 14일이다. 2025년 10월에 쓴 비교를 현재 공식 문서에 맞춰 재검토했다.

특히 Railway에도 이제 S3 호환 Storage Buckets가 있다. 따라서 “객체 스토리지가 없어 직접 운영해야 한다”는 설명을 그대로 적용하면 안 된다.

이번 비교에서는 공식 기능과 적용 조건을 정리했다. 같은 부하로 성능을 실험하거나 사용 요금을 새로 측정하지는 않았다.

| 항목 | AWS | Railway |
| --- | --- | --- |
| 서비스 구성 | EC2, S3, RDS 등 목적이 다른 서비스를 선택해 조합 | 소스·컨테이너·템플릿으로 서비스를 배포하고 볼륨·버킷 등을 연결 |
| 제어 범위 | 선택한 서비스에 따라 IAM·VPC 등 상세 설정 가능 | 프로젝트와 서비스 중심의 설정, 지원하는 네트워크 기능 안에서 설계 |
| 객체 스토리지 | S3 | 비공개 S3 호환 Storage Buckets |
| 운영 책임 | EC2와 RDS처럼 서비스별 책임 범위가 다름 | 플랫폼과 직접 배포한 앱·DB의 책임을 구분 |
| 확장 | 선택한 컴퓨팅·DB 서비스에 맞게 설계 | 한도 내 수직 확장과 설정한 복제본 수에 따른 수평 확장을 구분 |
| 비용 판단 | 서비스·리전·전송·보관·지원 비용을 합산 | 구독에 반영되는 사용료와 리소스·전송·스토리지 비용 확인 |

## 1. 서비스 모델 관점

AWS는 여러 클라우드 서비스의 집합이다. 서비스마다 사용자가 맡는 운영 범위가 다르다.

EC2에서는 운영체제와 애플리케이션을 직접 관리할 수 있다. RDS처럼 플랫폼이 운영 작업을 더 많이 맡는 서비스를 고를 수도 있다. 따라서 EC2까지 모두 “AWS가 패치해 주는 완전 관리형 서비스”로 묶으면 책임을 잘못 이해하게 된다. [AWS 책임 공유 모델](https://aws.amazon.com/compliance/shared-responsibility-model/)

Railway는 서비스 배포와 연결을 중심으로 구성한다. Docker 이미지뿐 아니라 GitHub 소스와 템플릿으로도 배포할 수 있다. 그래서 “반드시 Docker 이미지를 직접 만들어야 한다”는 조건은 없다.

초기 구성이 빠르다고 해서 배포 후 데이터 복구나 보안 업데이트까지 자동으로 해결되지는 않는다.

## 2. 인프라 구성 방식

AWS의 세밀한 IAM·VPC 설정은 복잡한 접근 정책이 필요할 때 판단 근거가 된다.

다만 초기 작업량은 선택하는 서비스와 기존 조직의 공통 구성에 따라 달라진다. 모든 AWS 사용자가 네트워크와 배포 파이프라인을 항상 처음부터 만들어야 하는 것은 아니다.

Railway는 프로젝트 안에 서비스를 배치하고, 환경변수와 네트워크 연결을 구성하는 흐름을 제공한다. 운영 전에는 DB 연결의 공개망 경유 여부, 서비스 간 통신 범위, 고정 외부 IP와 도메인 정책 지원을 요구사항과 대조한다.

UI가 간단하더라도 이 항목들은 보안 설계에서 따로 판단해야 한다. [Railway 비공개 네트워크](https://docs.railway.com/networking/private-networking)

## 3. 스토리지 및 파일 처리

AWS에는 목적이 다른 저장소 선택지가 있다. 객체 저장에는 S3, 블록 저장에는 EBS, 파일 공유에는 EFS를 쓸 수 있다.

“AWS 공식 스토리지만 사용할 수 있다”는 제한은 없다. 직접 운영하는 저장소를 선택할 수도 있지만, 그 경우 운영 책임도 함께 진다. [S3 개요](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)

Railway는 S3 호환 Storage Buckets를 제공한다. 따라서 객체 저장만을 위해 반드시 MinIO를 직접 배포할 필요는 없다.

Volume과 Bucket은 서로 바꿔 부르면 안 된다. Volume은 애플리케이션에 연결하는 영속 파일 저장 공간이다. Bucket은 객체 API로 접근하는 저장소다. [Railway Storage Buckets](https://docs.railway.com/storage-buckets)

현재 공식 문서는 버킷의 접근 방식, 리전, 연결 정보에 적용 조건을 둔다.

- 버킷은 비공개다. 파일 제공에는 서명된 URL 또는 백엔드 중계 등 접근 방식을 설계해야 한다.
- 버킷 생성 후 리전은 바꿀 수 없다. 앱·사용자와의 거리, 데이터 위치 요건을 먼저 확인한다.
- 연결 주소·인증정보와 URL 스타일은 해당 버킷의 Credentials 안내를 따른다. S3 호환이라는 말이 AWS S3의 모든 부가 기능과 완전한 동등성을 뜻하지는 않는다.

예를 들어 블로그 공개 이미지 URL을 장기 보관해야 한다면, 만료되는 서명 URL을 MDX 본문에 그대로 저장해도 되는지부터 판단한다. 이어서 접근 제어가 있는 중계 경로나 별도 공개 제공 구조가 필요한지 검토한다. 기존 S3 연동 코드의 API·CORS·캐시 요구사항도 확인한다.

이 글에서 실제 버킷 이전을 수행하지는 않았다.

## 4. 데이터베이스 제공 방식

AWS RDS는 유지보수 기능을 제공한다. 그래도 애플리케이션 호환성, 업데이트 일정, 백업 보존과 복구 가능성은 사용자도 따져 봐야 한다. 실제 엔진과 설정에 따라 적용 동작을 확인해야 한다. [RDS 유지보수 문서](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_UpgradeDBInstance.Maintenance.html)

Railway는 PostgreSQL·MySQL·Redis 등의 템플릿과 고가용성 구성 선택지를 문서화하고 있다. 다만 “DB를 띄우기 쉽다”와 “내가 필요한 운영 보장이 기본으로 갖춰져 있다”는 별개의 판단이다.

선택한 템플릿에서는 버전, 복제·장애 전환 방식, 업데이트 책임을 읽어야 한다. [Railway 데이터베이스 문서](https://docs.railway.com/databases)

Railway에는 볼륨 백업 기능도 있다. 그래서 백업을 전부 수작업으로 만들어야 한다는 설명은 과도하다.

다만 백업 일정·보존 범위·복원 절차는 설정해야 한다. 실제로 필요한 시점까지 데이터를 복구할 수 있는지도 확인해야 한다. [Railway 백업 문서](https://docs.railway.com/volumes/backups)

## 5. 배포와 CI/CD 경험

AWS에서 CodePipeline·CodeBuild·GitHub Actions를 조합하는 방식은 여러 배포 선택지 중 하나다. AWS의 모든 서비스를 이 방식으로만 배포해야 하는 것은 아니다.

App Runner는 소스 또는 이미지 기반 배포를 제공해 왔다. 현재 공식 문서는 신규 고객의 이용이 종료됐고 기존 고객은 계속 이용할 수 있다고 안내한다. 따라서 신규 도입의 일반적인 추천 예시로 삼으면 안 된다.

같은 공지는 대안으로 ECS Express Mode를 안내한다. 공지에 따르면 ECS Express Mode를 쓰려면 컨테이너 이미지와 IAM 역할을 준비해야 하고, 생성되는 AWS 리소스 비용도 든다. [App Runner 이용 변경과 ECS Express Mode 안내](https://docs.aws.amazon.com/apprunner/latest/dg/apprunner-availability-change.html)

Railway의 GitHub 자동 배포는 저장소·브랜치 연결과 배포 조건을 설정하는 기능이다. 자동 배포가 켜져 있다는 사실만으로 테스트 성공, DB 마이그레이션 성공, 정상 응답까지 보장되지는 않는다.

CI 검사 대기와 상태 점검은 배포 정책에 맞게 구성해야 한다. PR 환경도 사용하는 플랜과 환경 설정을 확인하고, 데이터가 분리되는 범위를 따로 검토한다. [Railway GitHub 자동 배포](https://docs.railway.com/deployments/github-autodeploys)

## 6. 네트워크 및 확장성

AWS는 다양한 리전과 컴퓨팅·네트워크 서비스를 조합할 수 있다. 다만 다중 가용 영역이나 다중 리전 기능이 있는 것만으로는 충분하지 않다. 내 서비스의 상태·DB·장애 전환까지 올바르게 구성했는지 따로 확인해야 한다.

Railway도 리전 선택과 여러 리전의 복제본 구성을 지원한다. 공식 문서는 자동으로 이루어지는 수직 확장과, 설정에서 복제본 수를 직접 늘리는 수평 확장을 구분한다.

따라서 “기본 오토 스케일”이라는 한 문장만 보고 복제본 수가 트래픽에 따라 자동으로 늘고 준다고 이해하면 안 된다. [Railway 확장 문서](https://docs.railway.com/deployments/scaling)

플랫폼을 선택할 때는 앱 리전 외에 DB·버킷 위치, 쓰기 지연, 세션 상태 공유, 저장소 제약도 같이 확인한다.

이 글은 두 플랫폼의 지연 시간을 직접 측정하지 않았다. 그래서 지역만 보고 어느 쪽이 더 빠르다고 결론 내리지 않는다. [Railway 리전 목록](https://docs.railway.com/deployments/regions)

## 7. 템플릿과 재현 가능한 구성

Railway의 공식·커뮤니티 템플릿은 시작 시간을 줄여 준다. 다만 이미지 출처와 버전 고정 여부, 환경변수, 볼륨·백업 설정은 검토 대상이다.

배포 버튼으로 바로 띄울 수 있는 템플릿이라도 공급망 검토는 따로 해야 한다.

AWS도 CloudFormation처럼 템플릿으로 인프라를 정의하고 재사용하는 도구가 있다. 따라서 “AWS에는 공유할 템플릿이 없고 모두 직접 작성해야 한다”는 식의 비교는 맞지 않는다.

비교할 대상은 템플릿이 있는지보다, 팀이 변경을 검토하고 같은 환경을 다시 만들 수 있는 방식이다. [CloudFormation 개요](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/Welcome.html)

## 8. 운영 책임과 지원

양쪽 모두 지원·SLA를 제품 이름 하나로 판정하면 안 된다. AWS는 이용하는 서비스와 지원 계약을, Railway는 가입한 플랜과 지원 경로를 확인해야 한다.

Railway에도 플랜에 따른 지원과 Enterprise 선택지가 있다. 그래서 “주로 커뮤니티만 지원한다”로 단정하지 않는다. [Railway 지원 안내](https://docs.railway.com/platform/support)

서비스를 선택할 때는 아래 질문에 답할 수 있어야 한다.

- DB가 멈추면 누가 복구하는가
- 백업 복원을 누가 수행하고 확인하는가
- 업무 시간 밖에 어떤 지원 경로를 사용할 수 있는가

SLA가 있어도 데이터 손실이나 장애는 발생할 수 있다.

## 9. 요금 체계 및 비용 예측

AWS는 실제 사용할 서비스와 리전의 가격을 조합해 산정한다.

Railway는 기본 구독료가 사용료에 반영되는 구조다. 그래서 구독료와 포함 사용량을 중복 계산하지 않도록 해야 한다. 플랜별 한도와 사용량 단위는 [Railway 요금 문서](https://docs.railway.com/pricing/plans)를 기준으로 확인한다.

“Railway는 큰 서비스에서 반드시 비싸다”거나 “AWS는 항상 저렴하다”는 결론은 이 글의 근거로 낼 수 없다. 비교하려면 같은 조건에서 아래 표의 항목을 넣어 계산해야 한다.

| 비교 입력 | 확인할 내용 |
| --- | --- |
| 앱 실행 | 평균·최대 CPU와 메모리, 실행 시간, 복제본 수 |
| 데이터베이스 | 상시 실행 리소스, 저장량, 복제, 백업 보관 |
| 파일 제공 | 객체 저장량, 요청 수, 제공 경로와 전송량 |
| 환경 수명 | 운영·개발·PR 환경 개수와 미사용 환경 종료 시점 |
| 운영 요구 | 로그 보관, 지원 계약, 장애 대응에 필요한 팀 작업 |

특히 Railway Bucket의 비용 규칙과 앱 서비스의 전송 비용은 구분한다. 버킷에서 백엔드를 거쳐 파일을 제공하면, 버킷 요금만 비교해서는 전체 비용을 판단하기 어렵다. [Railway Bucket 과금](https://docs.railway.com/storage-buckets/billing)

위 표는 계산에 필요한 입력 목록이다. 이 블로그의 실제 월 청구액, 같은 부하로 비교한 절감률, 이전 비용을 측정한 결과는 담고 있지 않다.

## 10. 조건별 선택 기준

빠르게 서비스를 배포하고 연결하려면 Railway를 검토할 수 있다. 단, 필요한 데이터·네트워크·지원 조건이 Railway의 제공 범위에 들어와야 한다.

특정 접근 정책, 리전, 데이터 서비스가 중요하다면 AWS에서 필요한 조합을 검토할 이유가 있다. 기존 조직의 AWS 운영 기반이 중요한 경우도 같다.

예를 들어 이미지 업로드가 있는 블로그라면 공개 이미지 URL의 수명, 객체 접근 권한, DB 백업 복원, 비사용 환경 정리까지 확인한다.

내부 서비스라면 인증·외부 연결·감사 기록 요구를 먼저 적는다. 이런 조건에 맞는 구성을 비교해야 “쉬운 배포”와 “계속 운영할 수 있는 서비스”를 함께 평가할 수 있다.
